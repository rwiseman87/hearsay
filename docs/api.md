# API guide

The core serves a loopback REST and WebSocket API (axum) that the web UI consumes.

**Every endpoint's parameters, request bodies, status codes, and schemas live in the OpenAPI
document**, generated from the Rust route definitions and drift-checked by `make codegen-check`:

| Where | What |
|---|---|
| `GET /openapi.json` | Served by a running core. |
| `web/openapi.json` | The committed copy, regenerated by `make codegen`. |
| `http://127.0.0.1:<port>/docs` | Browsable console (`make rust-serve`), with try-it-out against the live core. |

This page covers what a schema cannot express: how to get a token, the loopback controls that gate
every request, the shared conventions, and the two routes that are not JSON — meeting audio and the
live-transcript WebSocket.

## Getting a token

The token is generated per `serve` process and is never reused across runs.

In development, the core prints the tokenized URL to stdout:

```
open: http://127.0.0.1:<port>/?token=<token>
```

In the packaged app the token never reaches a log or a terminal: the core writes `{port, token}` to
a `0600` handshake file, the desktop shell reads it once, deletes it, and navigates the webview to
that URL. The SPA then keeps the token in memory only — never in `localStorage` or `sessionStorage`.

## Loopback hardening

Loopback is not a security boundary: any local process, and any web page in the user's browser, can
reach `127.0.0.1`. Three checks gate every request.

| Check | Rule | On failure |
|---|---|---|
| Bearer token | REST requires `Authorization: Bearer <token>`. The audio route and the WebSocket accept `?token=<token>` instead, because neither channel can set a header. Compared in constant time. | `401` |
| Host | The `Host` hostname must be `127.0.0.1`, `localhost`, or `::1`, which blocks DNS rebinding. | `400` |
| Origin | A present `Origin` must be loopback, which blocks cross-site requests and WebSocket hijacking. | `403` |

Non-browser clients such as curl send no `Origin` and pass that check; the token is the real gate.
The core also refuses to bind a non-loopback address unless `ENVIRONMENT=development`.

Every response carries `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, and
`Referrer-Policy: strict-origin-when-cross-origin`. Each request gets an `X-Request-Id` and one
access-log line with the token redacted. Database and internal failures render as a literal
"internal error"; details go to the log only.

## Conventions

- The REST base path is `/api`. Times are ISO 8601; segment `start_s` and `end_s` are seconds
  relative to the meeting start, not wall clock.
- List endpoints return `{ "total", "page", "page_size", "items" }` and take `page` (at least 1,
  default 1) and `page_size` (1 to 200, default 50).
- Errors return `{ "detail": "..." }`.

```sh
curl -H "Authorization: Bearer $TOKEN" http://127.0.0.1:8137/api/meetings
```

## Serving the UI

When the web bundle has been built (`web/dist` present), the core also serves it. `GET /` returns
`index.html` with the session token injected as `window.__HEARSAY_TOKEN__` behind a per-response CSP
nonce, and hashed assets are served from `/assets`. Without the bundle, the core runs API-only.

`GET /` requires the `?token=` query parameter and the loopback Host/Origin checks, so a cross-site
page cannot fetch it and therefore cannot read the injected token.

## Meeting audio

```
GET /api/meetings/{id}/audio
```

Serves the meeting's recording: one timeline-accurate stereo track, Me on the left channel and Them
on the right. Sample N is meeting second N/16000, so a segment's `start_s` maps directly onto an
`<audio>` element's `currentTime`.

- Takes `?token=` (an `<audio>` element cannot set a header) or a bearer header.
- Supports `Range` requests, answering `206 Partial Content`, so the browser can seek.
- The file is `audio.wav` until the archival sweep compresses it, then `audio.flac` — losslessly, so
  the samples are identical either way. The content type reflects which one it is (`audio/wav` or
  `audio/flac`); both decode natively in the shipped webviews.
- `404` if the meeting is unknown, or was recorded with audio retention off.

## WebSocket: the live transcript

```
ws://127.0.0.1:<port>/ws/meetings/{id}?token=<token>
```

Auth happens at the HTTP handshake, before the upgrade: a non-loopback `Origin` returns `403` and a
bad token `401`. Connecting to a meeting that is *not* the active recording session accepts the
socket and then closes it cleanly (code 1000), so a client can tell that apart from an auth failure.

While connected, the server pushes one JSON object per text frame.

### Transcript events

```json
{ "kind": "partial", "stream": "them", "speaker_label": "Them",      "text": "your car is on its",      "start_s": 28.4, "end_s": 29.2 }
{ "kind": "final",   "stream": "them", "speaker_label": "Speaker 1", "text": "Your car is on its way.", "start_s": 28.4, "end_s": 30.0 }
```

The client contract:

- `partial` events stream during ongoing speech and are **never persisted**. `final` events are
  written to the database and `transcript.md` before they are broadcast.
- Render by `(stream, start_s)`, and replace a stream's partial with that stream's next final.
- Me is always `"Me"`. Them partials carry the generic `"Them"` because the diarizer only assigns a
  speaker at turn end; Them finals carry the diarized label (`Speaker N`, or a bound name).
- After a rename or a per-line reassignment, re-fetch `/speakers` and `/segments` to pick up the new
  labels — the socket does not retroactively relabel what it already sent.

### Service events

```json
{ "kind": "status",         "state": "warming" }
{ "kind": "resync" }
{ "kind": "prompt",         "silent_seconds": 300 }
{ "kind": "capture_health", "state": "silent" }
{ "kind": "capture_state",  "state": "paused" }
{ "kind": "level",          "stream": "me", "rms": 0.12 }
```

- **`status`** — sent on connect when the transcription sidecars are still loading their models (a
  cold start), and again with `ready` once they finish, so the UI can show and clear a "preparing"
  notice.
- **`resync`** — this subscriber fell behind and the broadcast buffer dropped events. Because finals
  are persisted *before* they are broadcast, the database is a superset of the stream: re-fetch
  `GET /api/meetings/{id}/segments`, backfill, and keep streaming. The socket stays open.
- **`prompt`** — no speech on either stream for `silent_seconds`, so the UI shows a "still
  recording?" banner. Also sent on connect when a prompt is already active. If the silence continues
  to the end threshold the meeting auto-ends with a logged transcript marker;
  `POST /api/meetings/{id}/keep-recording` resets the clock. Both thresholds are configured in the
  `recording` settings section.
- **`capture_health`** — the mic signal path went digitally silent (sustained exact-zero samples,
  which a working mic never produces): `state: "silent"`, cleared with `"ok"`. The UI warns rather
  than showing the confident nonsense ASR produces from a dead signal. Mic only — the Them loopback
  is legitimately silent whenever nothing is playing.
- **`capture_state`** — the meeting was paused or resumed: `state: "paused" | "active"`. Also sent on
  connect when the meeting is already paused, so a window reopened mid-pause reflects it.
- **`level`** — recent RMS amplitude (`0.0..~1.0`) of a capture `stream` (`"me" | "them"`), pushed
  about ten times a second to drive the input waveform. Ephemeral: never persisted, never replayed to
  a new subscriber.
